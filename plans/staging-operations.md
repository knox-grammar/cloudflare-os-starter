## Decision

Use a **persistent, independently named seven-Worker staging stack** rather than `wrangler dev` or a Preview on each production Worker. One wrapper generator remains authoritative for both environments. GitHub Actions verifies every PR without credentials, and a separately approved staging workflow deploys one exact commit. Production keeps its own manual environment approval and requires evidence that the *same* commit passed staging. No automatic production deployment on merge.

Why: current Worker Previews isolate each Worker's Durable Objects, but Preview service bindings still target the bound Worker's **production deployment**, not a sibling Preview. KV and R2 also remain shared if bound to production IDs. The checked-in wrapper uses seven service-bound Workers and disables preview URLs on every backend; the pinned upstream preview script is for a different 18-Worker topology and relies on an unreleased Wrangler build. Local upstream `run-local` uses local password auth and does not include this wrapper's Microsoft Gatekeeper or Access identity. Neither is sufficient to rehearse Knox's existing-data migration.

## One maintainable wrapper, two explicit configurations

Implementation state: the separate config, target selector, isolation tests and CI dry-run are implemented on `staging/isolated-deploy`; hosted CI passed for the initial config-only branch. The operator subsequently approved reusing the production Microsoft authority and AI Gateway, so the staging config now explicitly models that exception while `staging.releaseReady` stays false. `pnpm deploy:staging` still stops before any remote mutation. No staging resources were provisioned. A real staging deployment workflow awaits Access, OAuth, credential-bootstrap, cost and provisioning review. The design is:

1. Keep `deployment.jsonc` as the **production** control surface. Add a complete, annotated `deployment.staging.jsonc` containing the seven approved staging Worker names, Access issuer/audience/admins, origin, AI mode, explicit staging storage identities after first provisioning, and non-secret policy values. Do not infer staging resource names by string replacement in production config. Staging's `Access.audience`, route, admins, `sharingDomain`, resource IDs and **explicitly shared** OAuth/AI authorities are reviewable data boundaries.
2. Extend `scripts/deploy.ts` with an explicit target selector (`--target staging` for `pnpm check:staging` / `pnpm deploy:staging`; existing `pnpm check` / `pnpm deploy` keep targeting production). Both paths call the same validation, config generator, build list, deploy order and cleanup. A staging assertion refuses production Worker names, hostname, Access audience, storage IDs/names and Context sharing origin. It accepts only an explicit, exact match for the operator-approved shared AI Gateway and Microsoft tenant/site. A production assertion refuses staging overrides. No arbitrary config-file or account override in CI.
3. Add tests to generate **both** environments' seven configs and compare the binding graph, migration tags and HTTP exposure; fail on any cross-environment service target, storage identity, hostname or audience, while verifying approved external-service reuse. Preserve upstream migrations; dry-run both with the pinned Wrangler. Ensure one check/deploy process per checkout; use separate worktrees for baseline-vs-upgrade rehearsals.
4. Staging GitHub Environment and manual workflow: separate secret `CLOUDFLARE_API_TOKEN`, exact SHA input, reviewer and branch restriction; run `pnpm check:staging`, deploy, record seven resulting Worker versions, run safe automated negative Access/route probes and request manual positive/admin checks. No prod token in the staging job. Scope tokens to the account/zone as narrowly as Cloudflare supports, and confirm target account before execution. Avoid leaking token or test-user data to logs.
5. Production workflow remains manually approved; enhance its release record/checklist to link the **same SHA** and staging evidence. The current workflow does *not* enforce staging promotion automatically. Do not make a successful `pnpm check` synonymous with production approval; GitHub Environment approval is the final human gate.

## Continuous cadence

- For each upstream release: select a *full* pinned commit; review auth, DO migrations and storage, RPC/bindings, catalogs and build steps; run root+submodule lint/tests and both dry-runs; stage the exact commit against persistent staging data; record version IDs and manual evidence; approve a production deployment of the same commit; verify live Access, data and models; update `DEPLOYMENT.md`. Separate staging/prod Github environments and permissions; no auto-sync with upstream `main`.
- For routine wrapper-only changes, run the same pipeline but scope manual tests to affected boundaries. Rehearse with synthetic persisted data on every state migration. Refresh staging fixtures periodically, never mirror production user content or tokens into staging state. Pin resource identities; shared Microsoft/AI usage cannot have independently isolated provider logs or billing, so account for staging usage explicitly. Retire old test data and Workers only after an explicit inventory and cleanup approval.
